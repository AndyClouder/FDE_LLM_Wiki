# 团队交互登记四要素

## 核心打法
团队之间的关系必须像 API 一样**显式登记**:模式 + 目的 + 每周投入 + 期限,并定期回看——**超期本身就是信号**。

## 操作步骤
1. 每段交互登记四要素:**交互模式(collaboration / X-as-a-Service / facilitating)、目的、每周投入小时/天、预计时长**;设 1-2 个月回看提醒
2. 尊重各模式的硬约束:一个团队**同时只与一个团队 collaboration**(间歇性协作的解质量与持续协作相当且更保多样性);XaaS 可多对多;facilitating 同时只与少数团队
3. **把别扭当信号判读**:本应低摩擦的 XaaS 却要天天泡在即时通讯里 = 组件边界/API/DevEx/能力缺口有问题(甚至说明平台团队自己需要 enabling);本应协作却无回应 = 价值理解、能力或边界雄心有问题
4. 演化路径:紧密 collaboration → 收窄主题的受限 collaboration → X-as-a-Service;在模糊接口上持续轻量协作,直到接口被证明稳定再切换
5. 用 Promise Theory 设计关系(遵守 SemVer 即承诺不破坏依赖者);Reinertsen:"注意角色之间无人认领的空隙"
6. FDE 应用:进场先 collaboration(共同探索)→ 中期 facilitating(传能力)→ 退场前 X-as-a-Service(沉淀物作为服务);"facilitating 六个月还没完"= 组织有病,多半是承接团队缺能力或边界错位——回到结构,不要加倍努力

## 验证案例
Team API 模板(Mooz 身份管理团队全例):团队名与焦点、类型、提供什么服务、服务级别期望(1 小时确认/24 小时首答)、负责的代码库、版本策略、聊天频道、站会时间、当前/即将交互的团队。
**Team API 七要素**(2026-08-20 第二轮补入):①代码(runtime endpoints/库/客户端/UI)②版本策略(**SemVer = 承诺不破坏依赖者**)③wiki 与文档 ④实践与原则 ⑤沟通方式(聊天/视频/站会)⑥工作信息(当前/接下来/优先级)⑦其他团队需要的一切——准绳是"他队能否仅凭此 API 与你协作"。
