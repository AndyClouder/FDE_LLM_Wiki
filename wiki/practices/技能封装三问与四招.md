# 技能封装三问与四招

## 核心打法
把"反复做、需要经验、值得固化"的工作流程封装成 AI 技能(SKILL.md + 可选脚本),让智能体稳定执行——从"手工作坊"进化到"自动化产线"。

## 底层逻辑(2026-08-20 第二轮补入)
- **智能体六大要素**:提示词(临时指令)/ 大模型(大脑)/ 上下文(工作记忆)/ 工具(能动手)/ 技能(怎么做)/ MCP(外部工具接入);一句话厘清:"工具让智能体能动手,技能教智能体具体怎么做,MCP 让外部工具无缝接入"
- **智能体 = 大模型 + harness(运行框架)**:框架负责加载技能、管理上下文、调度工具;技能里的脚本由框架本地运行**不经过大模型**——同一技能文件夹装进不同框架都能用
- 为什么需要技能:**"模型升级解决'能做好'(基础能力),技能解决'做得对'(业务对齐)"**;通用模型不可能猜透私人工作流,模型越强技能越值得投入

## 操作步骤
**先过三问**(不满足就别做):
1. **反复做吗?**——只做一次的事用提示词就够了
2. **对结果一致性有要求吗?**——希望每次不同的创意任务不需要技能;格式必须统一、检查必须同套的任务没有技能就是抽卡
3. **流程已基本稳定吗?**——自己还在摸索就别固化,否则把错误流程锁进 SKILL.md,每次调用都重复同一个错误

**三种不该做成技能**(排除项):
- 始终生效的规则 → 放全局配置(如 CLAUDE.md)
- 工具一行命令能搞定的 → 用工具(技能的价值在提供经验)
- 偶尔一次的任务 → 直接聊

**封装时的确定性拆分**:需要确定性的环节(数据清洗规则、精度、日期格式)写成脚本;判断性环节交给模型。

**设计四招**(对抗"用着用着才暴露"的问题):
1. **踩坑点(gotchas)**:把反复犯的错专门写进文件——Anthropic 内部几百个技能的实践表明,信息密度最高的部分往往不是流程说明,而是踩坑点
2. **可容错**:假定一定出意外——开头检查、人工确认点、中间结果存盘
3. **可扩展**:支持组合或外挂配置,新需求不改主文件
4. **跨对话记忆**:单独维护记录文件,下次接续上次进度

**迭代用评测循环**:客观标准保下限、人眼验收拔上限、新旧版本对比打分指导修改。

## 验证案例
作者的翻译流程封装:抓取网页→术语分析→分块翻译→拼接→审查润色全自动;配图/封面/访谈稿技能可组合(串联/并联/循环 + 子智能体)成写作工作流。

## 全书精读补充(2026-08-20)
- **需求卡 6 问**(5 分钟出骨架):问题 / 场景 / 输入 / 输出 / 规则 / 禁止清单——6 个答案基本就是 SKILL.md 的骨架;需求不需要完美,先跑起来由真实痛点驱动演进
- **技能四阶段**:MVP 跑通(第一版越简单越好,"能用"是唯一指标)→ 功能补齐(做加法)→ 架构重构(做拆分:SKILL.md 臃肿抽 references/,或一拆为二)→ 持续优化(没有终点);实例:小红书信息图技能从约 200 行经 20 多次迭代成 641 行主文件 + 26 个参考文档
- **四个心法**(结语):①好食材比好菜谱重要(技能装的是你的经验,模型不会自带);②先开火别等万事俱备(拆一拆总有能下手的环节);③你掌勺 AI 打杂(判断留人、执行交 AI);④**做过三次的事,其做法就值得写成技能**(沉淀的最小触发条件;不会写就找几篇好成品让 AI 反推菜谱)
- **任务拆三类操作**:执行规则(→脚本)/ 做判断(→模型)/ 调外援(→MCP);分工铁律:**需要判断的交给模型,需要执行规则的交给脚本**,粒度按"性质"不按"步骤"
- **"工具给能力,技能给经验"**:智能体知道 ffmpeg 的通用用法,不知道你们团队的规范(1080p、码率 5Mbps)——厂商产品给通用能力,FDE 的增量价值是补客户专属经验
- 三道安全闸:最小权限 / 二次确认(删除·发邮件·未知代码·敏感数据前暂停)/ 可追溯(记录所有操作配合 Git 回退);"信任不能代替安保"

**迭代两原则与三步验证**(2026-08-20 第二轮补入,Ch4):
- **迭代两原则**:①一次只改一个(控制变量,验证后再改下一个);②**解释原因比堆规则有效**("代码块是精确信息,插图会打断阅读节奏"能让智能体举一反三)——"底线用规则,偏好加解释"
- **三步验证**:①触发测试(5 条应触发 + 3 条不应触发的说法逐条测);②功能测试(同一输入跑 3 遍,看结构/关键信息/核心逻辑是否稳定,不必完全一致);③对比测试(有无技能各跑一遍,比交互轮数/出错次数/输出质量——差别不大说明技能还不够好)
- 改技能比改软件快的三个原因:智能体既是执行者又是修复者(就在现场)、拥有完整上下文(不用写 bug 报告)、文本配置天然好改
- 边界三分(语义/规则/混合驱动):提示词管一次性高灵活、脚本管 100% 确定可重复、技能管"反复做+既有死规则又需判断"的中间地带——不能互相替代
- 警惕 YAGNI:扩展性是跑通之后才需要考虑的,过早为"将来可能出现的需求"设计 = 过度设计;团队分发质量机制(Anthropic 内部):先沙盒试用或 Slack 推荐,获得足够关注再正式发布——不需要审核委员会,但需要"发布前有人用过、觉得好用"

## 适用信号
- 同一指令在不同对话里反复输入
- AI 输出质量像抽卡,交付标准不稳定
- 团队各自维护不同版本的提示词,无法同步更新
