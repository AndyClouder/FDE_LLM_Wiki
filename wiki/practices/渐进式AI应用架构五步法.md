# 渐进式 AI 应用架构五步法

## 核心打法
从最简架构(查询→模型→响应)起步,**按需逐级加组件**,不要一上来搭全家桶。生产验证过的演进顺序:

1. **增强上下文**:检索机制(RAG)+ 工具接入,让模型拿到必要信息——"context construction 就是基础模型时代的特征工程"
2. **上护栏**:
   - 输入护栏:PII/敏感信息检测(阻止或掩码脱敏,如 [PHONE NUMBER] + 反向字典还原),防泄密到外部 API、防恶意 prompt
   - 输出护栏:失败捕获(格式错/幻觉/毒性/敏感信息)+ 处置策略(重试 X 次 / 并行双发取优 / **人工兜底转移**)
3. **模型路由与网关**:意图分类 → 按类型分流(FAQ/人工/专用模型/便宜模型),管多模型复杂度与成本
4. **缓存降延迟**
5. **Agent 模式**:复杂逻辑与写操作

## 操作要点
- **可靠性 vs 延迟的护栏权衡**:护栏增加延迟,跳过护栏增加风险——两边都要量化,不拍脑袋
- **监控 false refusal rate**:系统可能"太安全"拦截合法请求,打断用户造成挫败
- **人工兜底的触发器**:情绪检测(愤怒→转人工)、轮次上限(防死循环)、特定短语
- 流式输出模式下,不安全内容可能在护栏判定前已推给用户——流式场景要特别设计
- Agent 可观测性:"Always print out each tool call and its output"——每个工具调用留痕可查,与 [[客服Agent全链路返审]] 的返审前提一致

## 可观测性与漂移(Ch10 全书精读补充)
- **log everything**:配置、最终 prompt、中间输出、每次工具调用及输出、崩溃时刻;trace 还原请求全链路
- **三指标**:MTTD(发现问题时长)/ MTTR(响应时长)/ **CFR(变更失败率)**——"不知道自己的 CFR 就该重造平台"
- **drift 三源巡检清单**:①系统提示变更(模板被同事改了 typo);②用户行为演化(用户学会写更简短指令 → 回复变短不是模型坏了);③**底层模型悄悄更新**(Voiceflow 因 GPT-3.5-turbo 版本变更意图分类掉 10%,同一变更却让 GoDaddy 客服 bot 变好)
- **缓存的隐私边界**:用户相关与时效性查询不该缓存——真实案例:退货政策回答含用户 X 会员信息,被缓存后泄露给用户 Y;semantic cache 阈值难调、误判返回错答案,高风险场景慎用
- 起步先不用编排器:"An orchestrator can abstract away critical details of how your system works, making it hard to understand and debug"

## 适用信号
- 新 AI 应用立项(避免过度架构)
- 已有系统要补安全与稳定性(从第 2 步护栏切入)
