# Demo 与生产系统的鸿沟

## 一句话内核
**Demo 能跑,不等于能投产。** 演示验证的是最好情况下的可行性,投产验证的是最坏情况下的可控性,两者是不同的工程问题。

## 展开
- 演示环境:干净数据、低错误容忍成本、无回滚要求、单次成功即可
- 生产环境:脏数据分布、错误直接作用业务、必须可回滚可观测、长期稳定运行
- 跨越鸿沟需要的不是"再调调 prompt",而是一整套工程化方法:评测体系、护栏、分级权限、回滚机制

## 技能版鸿沟印证([[图解Skill-AI提效实战指南]] Ch6,2026-08-20)
给自己用的技能打包发给朋友**全翻车**:朋友 A 英翻中不错、其他语言不行(日常只用英翻中,从没考虑多语种);朋友 B 配图技能不能画图(作者配了私有 Gemini API Key);朋友 C 上传 PDF 流程卡死(只传过 Markdown,无异常输入容错)。——**给自己用 = 基于大量使用经验的隐含假设;给别人用,这些假设大部分不成立**(同程序员自测没问题、用户手里全是 bug)。配套发布三级场景要求逐级叠加:自用(安全清单)→ 团队(**"发布前有人用过、觉得好用"**是最小质量机制)→ 社区(向后兼容、清理密钥、清理绝对路径)。软件工程五阶段(需求→设计→实现→测试→上线)完全适用。
