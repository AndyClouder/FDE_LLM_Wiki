# 拓扑演化三触发器

## 一句话内核
重要的不是某个时刻的组织形态,而是"改组织的决策规则"——三个触发器出现,就该重组承接结构。

## 展开
| 触发器 | 症状 |
|---|---|
| **1. 软件大到超出一个团队** | 创业公司超 15 人;其他团队长期等一个团队;变更总落到同几个人(隐性专业化 → 瓶颈);缺文档 |
| **2. 交付变慢** | 成员主观感觉变慢;速率/吞吐同比下降;"以前更简单";在制品持续堆积、大量变更等别的团队(QA 集中化即制造硬依赖);技术债使小改动即回归 |
| **3. 多个业务服务依赖大量底层服务**(金融/保险/政务典型) | 解法两件套:①**平台包裹层(platform wrapper)** 把底层服务与 API 平台化,提供一致 DevEx(关联 ID、健康检查、SLO、诊断 API);②每个高层业务服务由 stream-aligned 团队持有,自带"刚好够用"的遥测与诊断包装 |

- 组织感知(organizational sensing):稳定的团队 + 明确定义的交互 = 组织的神经系统,应持续自问:用户行为是否被误解?交互模式该不该换?X 还该不该自建?A/B 的紧协作还有效吗?C 团队的流被什么卡住?
- 拓扑以月为单位缓慢变化,不每天变;uSwitch:"我们不是因为想用 Kubernetes 才改组织,而是因为想改组织才用了 Kubernetes"

## 关联
