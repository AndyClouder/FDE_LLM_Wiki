# 业务结果导向

## 一句话内核
衡量单位决定行为:**以业务结果为导向,而不是产出物**。交付一堆东西、业务毫无变化,等于白干。

## 展开
- Build Trap:组织用产出物数量(功能数、文档数、评分)证明价值,业务侧却看不到变化
- 评分制评审是加速器:分数可以互抵,等于没设门
- 结果导向的落地形态:不可互抵的判定门 + 明确的"过门标准",规则不为结果背书

## 原书确认(2026-08 深度摄取)
[[Escaping the Build Trap]] 原文定义:"Build Trap 是组织困在用产出(outputs)而非结果(outcomes)衡量成功"。落地形态:战略阶梯(见 [[战略阶梯从愿景到团队目标]])+ [[Product-Kata六问]] 流程。转型失败第一原因:领导层口头要结果,实际仍按"发布了多少功能"考核。销售驱动型组织(合同定义路线图,"30 个没人用的功能")是最典型变体。

## 全书精读补充(2026-08-20):度量设计
- **原书定义**:Outputs = 可量化的产出物(功能数、发布数、velocity);Outcomes = 交付后问题被解决而产生的东西——真正的价值只在 outcomes 中实现(机制详见 [[价值交换系统]])
- **Vanity → Actionable**:累计用户数、page views 只涨不驱动决策;加时间分量(如"周活环比")变成 actionable;故事点/功能数是生产力指标,不是产品指标
- **两套指标框架**:Pirate Metrics(AARRR:获客/激活/留存/推荐/收入)与 HEART(幸福/参与/采用/留存/任务成功)
- **先行 vs 滞后指标**:留存是滞后指标,须配激活/满意度等先行指标——"防止冷数据到来时的意外";FDE 投产方案必须自带先行指标仪表盘,业务结果(滞后)没到之前先看先行指标是否在动(与 [[评测驱动开发]] 同构)
- **mutually destructive pairs(制衡指标对)**:追获客必须盯留存下限;单一指标必然被 gaming(呼应 [[系统杠杆点]]:规则层与目标层)
- 先基线后目标(Marquetly:留存 40%@6 月、二课率 10%,据此推出"留存 70% + 获客翻倍 ≈ 年增 $8M")

## 跨源印证:目标错位基模([[Thinking in Systems]] Ch5,2026-08-20)
"**系统有一个可怕的趋势,即只会产出你要求它产出的结果**"——以军费定义国家安全 → 军备竞赛;以放环数量考核计生 → 强行放环;以 GNP 定义经济成就 → 把事故医疗费、雇人育儿都算增长(GNP 衡量吞吐量/流量而非财富/存量)。对策:**让目标与指标反映系统真正的福利,特别小心不要将努力与结果混淆,否则系统只产出特定的努力**。帆船寓言:围绕规则极度优化的美洲杯赛艇"失去了所有适应力",规则一变即成废物。本概念由此获得独立第二源(原书 Build Trap + 系统论)。
