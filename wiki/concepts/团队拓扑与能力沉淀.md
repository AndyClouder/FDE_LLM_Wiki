# 团队拓扑与能力沉淀

## 一句话内核
协作结构决定能力归属:**能力依附于团队结构,而不是个人英雄**。没有承接设计的项目,做完就把 FDE 变成永久接口。

## 展开
- FDE 的隐痛:项目交付 = 你成为人肉 API,所有后续请求仍经你的手
- 根因在结构:立项时的模糊归属("材料团队 / 联合推进")= 没有接盘人
- 解法在结构:明确的唯一承接人 + 交接标准,能力才能从个人迁移到团队

## 行业印证(2026-08)
[[FDE模式行业观察与实践]] 把"沉淀与否"上升为 FDE 与外包的分界线([[FDE试金石]]):只留系统=外包,沉淀为 Skill/模板/产品=可规模化 FDE;并给出组织级机制([[本体反馈单与内部结算]]、矩阵制归属、绩效双轨)。相关组织陷阱见 [[坑7-沉淀缺失恶性循环]]。

## 原书确认(2026-08 深度摄取)
[[Team Topologies]] 给出完整框架(见 [[四类团队与三种交互模式]]):**FDE 对应 enabling 团队角色,其使命是让自己退出**("DevOps 型团队的目标是赋能组织其余部分,从而让自己没有存在的必要")。配套机制:康威定律(想要什么架构先设计什么团队结构)、认知负载核算(职责划分显式考虑团队认知容量)、Team API(用接口规范定义承接边界)。相关组织陷阱见 [[坑7-沉淀缺失恶性循环]]。

## 全书精读补充(2026-08-20)
- **TVP(最薄可行平台)**:"数字平台是自助式 API、工具、服务、知识与支撑的基座,作为有吸引力的内部产品存在"——平台可以只是一页 wiki;**客户若无平台团队,FDE 的沉淀物(模板、脚本、评测集)就是他们的 TVP 起点**;"开发者热爱造平台,没有强产品约束就会造得过大"(Kelly);平台要按生产系统对待(运行时间、事件响应、状态页)
- **内部定价调节需求**(Reinertsen):平台服务可分级、可用内部定价调节——与 [[本体反馈单与内部结算]] 的结算机制直接接续
- **platform wrapper**:多业务服务依赖大量底层服务时的沉淀形态(统一 DevEx:关联 ID/健康检查/SLO/诊断 API)
- **承接人必须是团队而非个人**:5-9 人、有成型时间(2 周-3 个月)的稳定小组;系统每一部分恰好归一个团队所有,"把代码当花园照料,不是当警察巡逻"
- 团队比例经验:stream-aligned 与其他类型之比约 **6:1 至 9:1**;架构团队至多是兼职 enabling 团队,职责是设计团队间 API 而非下颁设计

**唯一所有权与长寿团队**(2026-08-20 第二轮补入):
- **系统每一部分恰好归一个团队所有**;无共享代码所有权——外部团队可提 PR 但只有主队合并;"把代码当花园照料,不是当警察巡逻"
- 团队成型需 2 周-3 个月;Brooks 定律(加人不等于加产能);高信任组织成员 9-12 个月换队,一般 18 个月-2 年;毒性成员必须移除;**奖励整个团队而非个人**(Deming 主张废除年度绩效;Nokia 奖金按团队+公司业绩发)
- **平台是分形的**("乌龟叠乌龟"):平台自身由内部 stream-aligned/enabling/complicated-subsystem/更低层 platform 团队组成;**存量团队映射**:基础设施团队→platform;组件团队→拆入流式团队或并入平台或转 enabling/complicated-subsystem;工具团队→有截止日的 enabling 或平台一部分
